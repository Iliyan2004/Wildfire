1. Purpose and design principles

PAKFIRE is a wildfire spread simulator for the whole of Pakistan, built as a sister of SAILAB (flood) and LANDLAB (landslide). A user places an ignition on a map, the server builds a local grid from national datasets, fetches hourly weather, solves the earliest arrival time of fire at every cell, and returns animated results that a 3D viewer plays while its camera follows the fire. This document describes how that is put together: every process and module, every input and output path, the data formats, the libraries and external services, and the order in which the code runs. The physics and the validation record are in the separate PAKFIRE Technical Reference.

1.1 Principles that shape the code

  • One engine, three call sites. The same solver code (pkfire/solver.py over kernel_gpu.py and kernel_cpu.py) is used by the live application, by the instant footprint tier and by the validation, so a number seen in the interface and a number in the validation come from the same arithmetic. The adjustments applied before the solve live in one module (pkfire/adjust.py) for the same reason.
  • GPU first, then RAM, then CPU. solver.simulate tries the CUDA kernel (CuPy) and, if the GPU is missing or fails, runs the numba CPU kernel with the data in RAM. The reason for a fallback is recorded in the run metadata (gpu_error).
  • State lives in files, not in a database. A run is a directory data/runs/<run_id>/ of flat binary rasters and JSON; everything the viewer, the exposure analysis, the report and the time-lapse need is derived from it. Only the road network is read from a database (PostGIS, read-only).
  • One simulation at a time. A global lock (RUN_LOCK in app.py) serialises runs so that a shared GPU server stays calm; jobs queue and report progress.
  • Honest failure. A step that cannot run (no weather, no road database, no GPU) reports what failed in the response instead of inventing a value; transient failures are not cached.

2. System architecture

Three layers: a static single-page interface plus an iframe 3D viewer in the browser; one Flask process that owns the job queue, the run pipeline and all derived products; and the engine modules and datasets underneath. There is no message broker, no separate worker process and no database of runs.

3.4 Vendored physics modules pkfire/vendor/

Two modules written for FIRELAB (the Margalla platform that PAKFIRE grew from) are kept inside the package: pkfire/vendor/rothermel.py (Rothermel 1972 with Albini 1976 size classes and the Anderson and Scott & Burgan fuel models, imported by fuels.py) and pkfire/vendor/spotting.py (Albini 1983 coefficients and the Schroeder ignition probability, used by a test as the reference for the kernels). They need only NumPy. Everything else of the old FIRELAB platform (its other scripts, web pages, tests, documents, reference video and Tessera embeddings) was moved on 7 November 2026 to the folder Fire Simulation Model - FIRELAB legacy (archived 2026-11-07) next to this one and is not used by PAKFIRE.

7.1 Time and units

  • Simulation time is minutes from the start; weather arrays begin 48 h before the start (the lead-in, LEAD_IN_H), so hour h of the run is index 48 + h and kernels receive hour0 = 48.
  • Rothermel works in imperial units internally (lb, ft, min, BTU); fuels.build_tables converts spread rates to m/min and the kernels convert wind to ft/min.
  • Dates are naive UTC throughout; the interface converts to Pakistan time (PKT) for display.

8. Module internals

8.1 terrain.py

build_scene(lat, lon, half_km, cell_m, date) returns a dict: crs, transform, ny, nx, dx, dem, lc, fb, ftype, ndvi, ndvi_file, slope, upaz, fuel, cont. Each raster is read into the grid by _read_to_grid (rasterio warp, bilinear or nearest). lulc_path(year) picks the ESRI file of the year (clamped to 2017-2025); pick_ndvi_file takes the composite nearest in time when the date is within the record and otherwise the newest within 16 days of the day of year. load_canopy / canopy_for_scene read the national canopy raster (mean and 90th-percentile height) on demand, only when the canopy option is on. fuel_from_lulc maps the ESRI classes, NDVI, elevation and forest type to rows of the fuel table and computes the continuity factor (burnable fraction, desert and sparse-vegetation thresholds).

8.2 weather.py, moisture.py, fuels.py

  • weather.hourly(lat, lon, start, hours) → dict with temp, rh, wind (m/s), wdir, precip, source; fetches in chunks, caches every reply in data/raw/weather, falls back to MET Norway (6 s connect timeout), and when no weather history exists for the lead-in the first hour is held and the run records that in conditioning.
  • moisture.dead_moisture(temp, rh, rain) → (3, n) fractions for 1, 10 and 100 h fuels by Simard equilibrium moisture with exponential time lags and WRF-SFIRE-style rain wetting; ignition_probability is Schroeder (1969).
  • fuels.crown_cells(grid, tables, fuel_rows) gives the kernels the crown initiation intensity and bulk density per cell (from the grid when measured canopy is present, otherwise the per-fuel defaults); fuels.canopy_crown derives them from canopy height (CBH = 0.35 × p90 height, CBD = 0.15 × mean/p90, pine fuels only; assumed relations, Technical Reference Ch. 10.3). fuels.build_tables(m_dead, m_herb, m_wood) evaluates pkfire/vendor/rothermel.py for every fuel model and hour and returns the kernel tables: r0, ir (hour × row), and per-row B, C, E, ratio, slope_k, waf, tau, spot, sigma, spot_a, spot_b, crown_i0, crown_cbd. run._tables adds spot_ign and emc_pct.

8.3 adjust.py, windfield.py, microclimate.py, roads.py

  • adjust.apply(scene, w, params, hours, lead, user_wind, start) returns cont, wmod, wrot, w, moist, decay_min. Keys of the profile are grass, shrub, forest, wind, moist, road, road_minor, tmoist, chan, canopy, wfield, decay_h, suppress (Technical Reference Ch. 5.5); with canopy > 0 it also returns crown_ci0, crown_cbd per cell (fuels.canopy_crown from terrain.canopy_for_scene).
  • windfield.solve solves ∇²φ = −∇·u₀ with Jacobi-preconditioned conjugate gradients on a 240 m × 40 m Cartesian grid; the operator is a fused CUDA kernel (apply_A), the rest are CuPy elementwise kernels, with a NumPy fallback; returns speed ratio and rotation.
  • microclimate.moisture_delta / rate_multiplier / channel_strength: solar position, horizon angles, fuel temperature, equilibrium moisture difference and its conversion to a rate multiplier; stability index for channelling.
  • roads.road_factor(scene) reads the highway classes of the window from PostGIS, rasterises them and returns major and minor barrier factors and an ok flag.

8.4 The solvers

kernel_cpu.py (numba)kernel_gpu.py (CUDA via CuPy)
AlgorithmFinney minimum travel time: Dijkstra with an indexed binary heap, 16 neighbours, per-edge travel time from the Richards ellipseexact parallel band relaxation: relax kernel over hour bands inside bounding-box regions until no cell changes, then finalize (intensity, spotting)
Rate at a cell_cell: r0 (hour, row) × continuity × burn-out; wind × WAF × terrain ratio; slope and wind vector; ellipse length-to-breadth; Byram intensity; Van Wagner / Cruz crown fire (initiation intensity and bulk density read per cell, cI0[i], cCBD[i])cellp: the same arithmetic in CUDA; struct P of device pointers (fuel, slope, upaz, cont, wmod, wrot, tdec, tables)
Spottingmax_spot_m (Albini 1983) per finalised cell; log-normal landing with Schroeder test; deterministic seedmax_spot_m and a hash RNG (hsh, u01) in finalize
Single / batchsimulatesimulate and simulate_batch (blockIdx.y = ensemble member; _derive_batch prepares per-member tables)
Outputarrival (min), head spread rate, intensity, spot listsame, as CuPy arrays copied back

solver.simulate calls the GPU first when kernel_gpu.available(), catches any failure, records it as gpu_error and re-runs on the CPU. In single runs the CPU solver is as fast as or faster than the GPU for the grid sizes used; the GPU wins for large grids and batched ensembles.

8.5 Exposure, evacuation, overlays, reports

  • exposure.compute(run_id): people from WorldPop spread to the export grid, scaled by the PBS census factor of the ignition district (pbs_district, factor kept only in 0.7-1.5), housing and firewood shares, informal settlement area (_informal), and per-facility arrival or distance for hospitals, schools, grid stations and power lines.
  • evac.analyse(run_id, lead_min): loads the OSM road graph of the window (load_graph), picks the most populated 1 km cells near the burn, runs a time-dependent Dijkstra (_escape) with road loss from the arrival raster, bisects the latest departure, and computes drive time from fire stations to the ignition.
  • overlay.render(run_id, layer) makes the PNG layers (arrival, intensity, probability) with colour ramps; isochrones makes hourly GeoJSON contours; static_map_png a map image for reports.
  • report.run_pdf / batch_pdf build HTML (inline SVG charts) and render with WeasyPrint; timelapse.render draws frames with Pillow and encodes with ffmpeg.

12.2 Shared-server rules

GPU temperature is not guarded by the code (the guard was removed on request); runs are serialised by RUN_LOCK. The shared server has reset under sustained GPU load in the past, so long calibrations should be run with checkpoints (the calibration writes calib_<name>.json after every parameter).

12.3 Known operational gaps

  • The SimCity PostGIS (port 5455) is a separate project's service; when it is down roads are ignored and the evacuation panel reports 'road database unavailable'.
  • JOBS is in memory: a server restart forgets running and finished jobs (finished runs remain on disk).
  • Weather depends on the Open-Meteo and MET Norway services being reachable for runs that are not cached.
